## 2. コンセプト要約

スペシャルティコーヒーを飲む人が、カップを受け取って最初の一口を飲むまでの数十秒に使うプロダクトです。その人は豆のカードに書かれた「Anaerobic Natural」の意味が分かり、分かる自分を少し誇らしく思っています。しかし写真をそのままストーリーズに上げても、その一杯が何だったのかは写りません。このプロダクトは、写真に精製プロセスを主役としたデータを重ね、「何を飲んだかを分かって飲んでいる」ことが一目で伝わる一枚に変えます。満たす感情は、記録の達成感ではなく「この一杯を選んだ自分の目」を見せられる満足です。

**キャッチコピー案**
1. 一杯を、一枚に。
2. プロセスまで、写す。
3. 何を飲んだか、まで投稿する。

**サービス名：PROCESSHOT（プロセスショット）に決定（2026-11-14）。** 以下は決定前の検討メモ。
- 候補の方向性：(a) プロセスを名乗る語（例：PROCESSED）、(b) 一杯・一枚の単位を表す語（例：ONE CUP）、(c) @hakko.3d と地続きの語（例：HAKKO LOG）
- 決め方：次の4条件をすべて満たすものから依頼者が選ぶ。空き状況はいずれも未確認です。
  1. 欧文大文字で10文字以内（画像のワードマークが22pxでも読める）
  2. ドメインとInstagramハンドルが取れる
  3. J-PlatPatで同一・類似の商標がない
  4. 声に出して1回で伝わる

## 3. 画面設計

### 全体の流れ

```
S0 トップ → S1 写真 → S2 プロセス → S3 生産国 → S4 場所 → S5 プレビュー → S6 完了
                └────── S2〜S4は「あとで／スキップ」で飛ばせる ──────┘
```

- S2〜S4は、画面上半分に「作りかけのシェア画像」を常に表示し、選ぶたびに文字がその場で載ります。入力が作業ではなく、画像を仕上げる操作になります。
- 選択したら自動で次の画面へ進みます（「次へ」ボタンを押させない）。戻るは左上の矢印1つです。
- **タップ数の目標**：全項目を入れて保存まで **7タップ以内**（OSの写真選択画面内の操作と、店舗名の文字入力は除く）。写真だけなら3タップ。所要時間の目標は30秒以内。いずれも設計目標で、実測値ではありません。

| 経路 | タップの内訳 | 合計 |
|---|---|---|
| 全項目（下位プロセスあり・店舗は最近の店から） | はじめる1＋親1＋下位1＋国1＋店舗1＋店名1＋保存1 | 7 |
| 写真のみ | はじめる1＋「このまま作る」1＋保存1 | 3 |

### S0 トップ
- **目的**：3秒で「写真がこうなる」と分かり、すぐ始められること。
- **置く要素**（優先順）
  1. 完成したシェア画像の実例1枚（画面高の約60%。説明文の代わり）
  2. キャッチコピー1行
  3. 「はじめる」ボタン1つ（押すとそのままOSの写真選択が開く）
  4. フッター：「写真も記録も、この端末の外に出ません」の1行、プライバシー表記へのリンク、@hakko.3d へのリンク
- **置かない要素**：機能説明の箇条書き、スクロールしないと見えない内容、ログイン、複数の実例のカルーセル、Cookieバナー（Cookieを使わないので不要）
- **遷移**：はじめる → OSの写真選択 → S1

### S1 写真
- **目的**：写真を1枚決め、切り抜き位置を合わせる。
- **置く要素**：9:16の枠に収まった写真（ドラッグで位置、ピンチで拡大）／「この写真で進む」／「選び直す」
- **置かない要素**：フィルター、明るさ調整、複数枚選択
- **遷移**：進む → S2

### S2 プロセス（このプロダクトの主役の画面）
- **目的**：精製プロセスを選ぶ。
- **置く要素**
  1. 上半分：作りかけの画像（選んだ瞬間、プロセス名が大きく載る）
  2. 親4つの大きなボタン（2×2）：ウォッシュド／ナチュラル／ハニー／その他
  3. 親を選ぶと同じ画面の下に下位の選択肢が開く（別画面にしない）。先頭は「（親）のみ」
  4. 「わからない・スキップ」
- **置かない要素**：プロセスの解説文（将来枠）、検索欄
- **遷移**：ウォッシュドは選択即 S3。それ以外は下位を選んだ時点で S3

### S3 生産国
- **目的**：国を1タップで選ぶ。
- **置く要素**：作りかけの画像／最近選んだ国（最大3）／主要産地8つ／「ほかの国」（開くと五十音順の全リストと絞り込み欄）／「ブレンド」／スキップ
- **置かない要素**：地域・農園・品種の入力
- **遷移**：選択即 S4

### S4 場所
- **目的**：店舗名を入れる、または自宅と示す。
- **置く要素**：作りかけの画像／「店舗」「自宅」の2択／店舗の場合のみ：最近の店（最大5）、店舗名の入力欄、「近くの店を探す」ボタン／スキップ
- **置かない要素**：地図、住所入力、ページを開いた時点での位置情報の許可要求
- **遷移**：確定 → S5

### S5 プレビュー
- **目的**：仕上がりを確認し、型と比率だけ選ぶ。
- **置く要素**：完成画像（画面の主役）／型の切替（A・B）／比率の切替（9:16・4:5）／「保存・シェア」／各項目をタップするとその入力画面に戻れる
- **置かない要素**：文字色・フォント・位置の自由編集（選択肢を増やすほど仕上がりが崩れるため）
- **遷移**：保存・シェア → OSの共有シート → S6

### S6 完了
- **目的**：保存できたことを伝え、次の一杯につなぐ。
- **置く要素**：「保存しました」／うまく保存できない端末向けの「画像を長押しで保存」表示／「もう一杯記録する」
- **置かない要素**：会員登録の誘導、評価依頼、他サービスへのシェアボタン群（OSの共有シートに任せる）
- **遷移**：もう一杯 → OSの写真選択 → S1

**試作との差**：リポジトリの `index.html` は全項目を1ページに並べた試作です。本設計はステップ型なので、実装時に組み替えます。項目・選択肢・写真の処理方法は試作のまま使えます。

## 4. シェア画像の設計（最重要）

### 4.1 Stravaの画像の「かっこよさ」の分解

1. **主役が1つだけある**：距離などの数値1つが極端に大きい。見た瞬間に読む順が決まる。
2. **大小が2段階しかない**：「小さく字間の広いラベル」と「大きく太い値」の対だけで全体が組まれ、中間サイズがない。
3. **色は白1色**：文字を箱や帯で囲まず、写真に直接置く。読みやすさは写真側を暗くして確保する。
4. **副次データは横一列に等間隔**：グリッドに揃っていることで計測器のような信頼感が出る。
5. **写真が主役で、データは3分の1以下**：情報を載せても「自分の写真」のままである。
6. **ロゴは小さく、必ず同じ位置**：邪魔をしないが、どのサービスの画像かは分かる。

### 4.2 このプロダクトへの翻訳（文法として取り入れる）

Stravaの主役は「数値」ですが、コーヒーの一杯には誇れる数値がありません。主役の座に **プロセス名** を置きます。これが「プロセスを主役にする」の画像上の実体です。

- 主役：プロセス名（最大2行）
- 副次データ：ORIGIN／PLACE／DATE を横一列に
- ラベルと値の2段階だけで組む。文字は白1色（型Bのみ地色に応じて墨1色）

### 4.3 共通ルール（基準は1080×1920。4:5は4.6）

**データの優先順位**：① プロセス ② 生産国 ③ 場所 ④ 日付 ⑤ ワードマーク

**安全域**：上250px・下250pxには文字を置かない（ストーリーズでアカウント名や返信欄に隠れる範囲の目安。実機で要確認）。左右の余白は72px。文字の置ける幅は936px。

**タイポグラフィの階層**

| 役割 | サイズ | ウェイト | 字間 | 備考 |
|---|---|---|---|---|
| 主役（プロセス名） | 132px | 800 | -0.01em | 行送り0.95。全大文字。最大2行 |
| 副次の値 | 44px | 600 | 0 | 全大文字（店舗名は入力のまま） |
| ラベル | 26px（副次列は22px） | 600 | 0.16em | 全大文字。不透明度70% |
| ワードマーク | 22px | 700 | 0.12em | 不透明度80% |

大小比は 主役：副次の値：ラベル ＝ 約 5：1.7：1。中間サイズは作りません。

**主役の文字列の決め方**
- 1行が936pxに収まらないときは、収まるまで文字を縮める（下限72px）。
- 下位を選んだ場合は「下位／親」の2行。親の語を含まない場合は、親をラベル行に添える。

| 選択 | ラベル行 | 主役（／は改行） |
|---|---|---|
| ウォッシュド | PROCESS | WASHED |
| ナチュラル | PROCESS | NATURAL |
| ナチュラル＞アナエロビック | PROCESS | ANAEROBIC／NATURAL |
| ナチュラル＞カーボニックマセレーション | PROCESS · NATURAL | CARBONIC／MACERATION |
| ナチュラル＞インフューズド／コーファーメント | PROCESS · NATURAL | INFUSED /／CO-FERMENT |
| ハニー | PROCESS | HONEY |
| ハニー＞イエロー・レッド・ブラック | PROCESS | YELLOW（RED・BLACK）／HONEY |
| その他＞サーマルショック | PROCESS | THERMAL／SHOCK |
| その他＞デカフェ | PROCESS | DECAF |
| その他＞スマトラ式 | PROCESS | WET-HULLED |
| その他＞自由入力 | PROCESS | 入力のまま（和文は主役サイズの0.8倍） |

**空の項目の扱い**
- 副次データは、空の列を詰めて左寄せにする（列幅は固定のまま）。
- プロセスが空のときは、生産国を主役に繰り上げる（ラベルは ORIGIN）。生産国も空なら店舗名、それも空なら日付だけを副次の行に出し、主役なしとする。
- 店舗名が長いときは1行に収め、収まらない分は末尾を「…」にする（全角14文字が目安）。

**日付の書式**：`2026.11.14`（数字とピリオドのみ。言語に依存しない）

**ワードマーク**：PROCESSラベル行の右端に、ラベルと同じベースラインで置く。位置は型A・Bで共通。ワードマークは「PROCES」を太さ500、「SHOT」を太さ900で組み、読みの区切りを見せる。ワードマークの右に、アカウント名 `@hakko.3d` を小さく（18px、不透明度70%）併記する（2026-11-14 のフィードバックで追加）。

### 4.4 型A「FULL」（既定）

- **写真との関係**：全面。写真が画像そのもので、文字は左下に直接載る。
- **読みやすさの確保**：画像の下半分（y=960〜1920）に、透明から黒65%へのグラデーションを敷く。箱・帯・文字の影は使わない。
- **配置**（左揃え、x=72）

| 要素 | 上端のy | 高さ |
|---|---|---|
| ラベル行（PROCESS ＋ 右端にワードマーク） | 1250 | 26 |
| 主役（2行時） | 1296 | 250 |
| 副次データの行（ラベル22＋間10＋値44） | 1594 | 76 |
| 文字ブロックの下端 | 1670 | — |

- 主役が1行のときは、ブロック全体を下端1670に合わせて下げる（上が125px空く）。
- 副次データは3列、各列の幅は312px（936÷3）。
- 文字ブロックの高さは420pxで、画像の約22%。写真が78%を占める。
- **この型の理由**：写真の力を最大に使え、ストーリーズで最も「自分の投稿」に見える。

### 4.5 型B「LABEL」

- **写真との関係**：フレーム。無地の地に正方形の写真を置き、下にデータを「標本ラベル」のように組む。暗い店内や逆光など、文字を載せると読めない写真の受け皿でもある。
- **地色**：紙色 `#F5F4F0`（文字は墨）または墨色 `#0E0E0E`（文字は白）。既定は紙色。S5で1タップ切替。
- **配置**

| 要素 | 位置・寸法 |
|---|---|
| 写真 | x=72, y=250, 936×936（正方形）。角丸なし |
| ラベル行（PROCESS ＋ 右端にワードマーク） | y=1250 |
| 主役 | y=1290〜、サイズ112px、最大2行（高さ213） |
| 罫線 | y=1535、太さ2px、幅936、不透明度20% |
| 副次データの行 | y=1567〜1650（ラベル22＋間10＋値40） |

- 型Aとの違いは、主役が112px、副次の値が40px、罫線が1本あること。それ以外の規則は共通。
- **この型の理由**：写真の出来に左右されず、プロセス名が必ず読める。フィード投稿にも向く。

### 4.6 4:5（1080×1350）への変換

- 安全域は不要（フィード投稿はUIが被らない）。余白は四辺72px。
- 型A：文字ブロックをそのまま、下端をy=1278に合わせる。グラデーションはy=675から。
- 型B：写真を936×702（4:3）にしてy=72に置く。ラベル行838、主役878〜、罫線1123、副次の行1155〜1238。

### 4.7 既定の縦横比とその理由

既定は **9:16**。理由は、(1) 主な出口がストーリーズであること、(2) @hakko.3d のフォロワーへ広がる最短経路がストーリーズのメンションであること、(3) スマホで撮った縦写真を切らずに使えること。4:5はフィード投稿用の切替として持ち、1:1は持ちません（選択肢を2つに保つため）。

### 4.8 書き出し

1080×1920（または1080×1350）のJPEG、品質0.92。端末の画面密度に関係なくこの寸法で固定します。

## 5. 入力フォーム設計

**項目順**：写真 → プロセス → 生産国 → 場所 →（日付は自動）

- **写真が最初**：写真が感情の起点で、以降の入力がすべて「この写真を仕上げる操作」になるため。
- **プロセスが2番目**：主役の項目を、集中力が最も高いうちに選ばせる。画像に最初に載る文字がプロセス名になり、差別化の核が体験の順番にも表れる。
- **日付**：今日の日付を自動で入れ、入力画面は作らない。変えたいときだけS5で日付をタップして変更する。

**選択式にするもの**

| 項目 | 出し方 |
|---|---|
| プロセス（親） | 4つの大きなボタン。常に全部見えている |
| プロセス（下位） | 親を選ぶと同じ画面に開く。先頭に「（親）のみ」。自由入力は「その他」の末尾に1欄 |
| 生産国 | 最近の3つ → 主要産地8つ（エチオピア、ケニア、コロンビア、ブラジル、グアテマラ、コスタリカ、パナマ、インドネシア）→「ほかの国」で全リスト。日本語で選び、画像には英語名で出す |
| 場所 | 「店舗」「自宅」の2択。店舗は最近の5つから1タップ |

主要産地8つは設計上の仮置きです。依頼者のフォロワーがよく飲む産地に合わせて差し替えてください。

**現在地 → 店舗候補の流れ**
1. S4で「近くの店を探す」を押したときだけ、位置情報の許可を求める。押さない人には一度も求めない。
2. 許可されたら、座標を小数第3位（約100m）に丸めてプロキシへ送る。
3. 近い順に最大5件を表示。選ぶと店舗名が入力欄に入る（後から書き換え可）。
4. 許可されない・4秒以内に応答がない・0件・検索が停止中のいずれでも、入力欄にカーソルを移し「店舗名を入力してください」とだけ出す。エラー画面は作らない。
5. 座標は検索の1回だけに使い、端末にも保存しない。選んだ店舗名だけが「最近の店」に残る。

店舗検索の提供元が決まるまでは、3の代わりに手入力と「最近の店」だけで公開できます。

**自宅記録の扱い**：「自宅」を選ぶと位置情報に関する処理は一切動きません。画像のPLACE列は「HOME」。地名は出しません。

**摩擦を下げる工夫**
- 選択即遷移で「次へ」を押させない。
- 2回目以降は、最近の国・店が先頭に出るので、いつもの店なら場所は2タップ。
- すべての入力がスキップ可能で、いつでも「このまま作る」でS5へ飛べる。
- 作りかけの画像が常に見えるので、入力するほど完成に近づくのが分かる。
- 途中で閉じても、写真以外の選択は同じタブの中では保持する（再読み込みで消える）。

## 6. ビジュアル設計の方向性

**カラー：上限4色**

| 役割 | 色 | 使う場所 |
|---|---|---|
| 墨 | `#0E0E0E` | 文字、ダーク時の背景、型Bの地 |
| 紙 | `#F5F4F0` | 背景、ダーク時の文字、型Bの地 |
| 灰 | `#8A8A86` | ラベル、補足、罫線（不透明度で濃淡） |
| 差し色 | `#FF4A1C`（朱） | 選択中の印、主ボタンの1か所のみ |

- 茶色は使いません。色は写真（コーヒー、カップ、店内）が持ち込むので、UIは無彩色で受けます。
- 差し色は1画面に1か所まで。シェア画像の中には使いません（画像は白または墨の1色）。
- プロセスごとの色分けは採用しません（色数の上限を破り、画像の統一感も崩すため。将来枠）。

**フォント**
- 欧文：Inter Tight に統一（画面UIとシェア画像のすべての文字。2026-11-14 のフィードバックで Inter との併用をやめた）。SIL Open Font License。自サイトから配信し、外部のフォント配信サービスは使わない。
- 和文：端末の標準フォント（iOSはヒラギノ角ゴ、AndroidはNoto Sans CJK）。店舗名にはどんな漢字も来るため、和文フォントを配信すると数MBになり、初回表示と通信量に響くためです。端末によって店舗名の字形がわずかに変わる点は受け入れます。
- 画面UIのサイズは3段階のみ：13px（ラベル）、16px（本文・入力）、28px（見出し）。

**角丸・線・影**
- 角丸：ボタンと選択肢は完全な丸端（高さの半分）、入力欄と写真枠は14px。この2種類だけ。シェア画像の中は角丸なし。
- 線：1px、灰の不透明度20%。区切りにだけ使い、囲みには使わない。
- 影：使わない。重なりは余白と線で表す。
- タップできる要素の高さは最低48px。

**ダーク／ライト**
- 画面UIは端末の設定に従う（墨と紙が入れ替わるだけ）。切替ボタンは置かない。
- シェア画像は端末の設定と無関係。型Aは常に写真＋白文字、型Bは紙色が既定。

## 7. 技術設計

### 7.1 構成の全体像

```
[利用者のブラウザ]
  ├─ 画面・画像生成・写真処理 … すべてここで完結
  ├─ 端末内保存（テキストの入力補助のみ）
  │
  ├──→ [静的ホスティング＋CDN]  HTML/CSS/JS/フォントの配信のみ
  └──→ [同一ドメインの薄いプロキシ]  店舗検索のときだけ
              └──→ [店舗検索の提供元API]
```

サーバー側にあるのは「ファイル配信」と「店舗検索の中継」の2つだけで、データベースはありません。

### 7.2 ブラウザ内での画像生成

- **方式**：Canvas 2D に直接描画する。順序は、写真 → グラデーション → 文字。HTMLを画像化する方式（DOMのスクリーンショット系ライブラリ）は、端末ごとに文字位置がずれ、依存も増えるので採りません。
- **フォント**：描画前に欧文フォントの読み込み完了を待つ。失敗したら端末の標準フォントで描く（生成は止めない）。
- **写真の取り込み**：選択されたファイルを画像として読み込み、Canvasに描き直す。この時点でEXIF（GPS座標、撮影日時、機種名）は引き継がれない。向きの情報だけ読み込み時に反映する。元ファイルはメモリ上でのみ扱い、どこにも保存しない。
- **書き出し**：CanvasからJPEGを生成。生成物には位置情報を含むメタデータは付かない。

### 7.3 保存・シェア

1. Web Share API（ファイル共有）が使える端末では、OSの共有シートを開く。ここからInstagramや写真アプリへ渡せる。
2. 使えない端末では、ダウンロードリンクで保存する。
3. どちらも失敗した場合に備え、S6に画像そのものを表示し、長押しで保存できるようにする。

### 7.4 ログインなしMVPの可否と保存

ログインなしで成立します。核機能に利用者の識別が不要だからです。端末内保存は次の3種類だけで、いずれも端末の外に出ません。

- 最近選んだ生産国（最大3）
- 最近入力した店舗名（最大5）
- 前回の画像設定（型・比率・地色）

保存先は localStorage。設定画面に「すべて消す」を1つ置きます。iOS Safariには、一定期間開かれないサイトの端末内保存を消す仕様があります（WebKit公式の情報で要確認）。消えても困らない入力補助だけを置く設計にしているのはこのためで、「記録が残る」とは謳いません。

### 7.5 位置情報・店舗データの取得方法

| 選択肢 | 長所 | 短所・要確認 | コスト感 |
|---|---|---|---|
| A. 手入力のみ | 外部依存ゼロ。プライバシー上の論点なし | 入力の手間 | 0円 |
| B. 商用の店舗検索API（Google Places、Foursquare 等） | 店舗の網羅性が高い | 従量課金。店舗名の保存・地図なし表示に規約上の制約があり得る | 無料枠の有無と単価は公式の料金表で要確認 |
| C. OpenStreetMap系 | データ利用の自由度が高い（帰属表示が条件） | 日本の個人店の網羅性は不明。公開サーバーは本番利用に制限があり、自前運用か有償ホスティングが必要 | 運用費は構成次第 |
| D. 国内向けの地域検索API | 日本の店舗に強い可能性 | 提供状況・規約・商用可否を要確認 | 要確認 |

**設計上の決定**：公開時はAで出し、B〜Dは依頼者のリサーチと公式ドキュメントの確認後に選びます。どれを選んでもプロキシの先を差し替えるだけで済むよう、ブラウザとプロキシの間の約束事を固定します（送る：丸めた緯度・経度。返る：店舗名と距離の最大5件）。料金の具体額は未確認なので書きません。

### 7.6 スマホブラウザでの制約

| 制約 | 対処 |
|---|---|
| 位置情報はHTTPSかつ利用者の許可が必要 | 全ページHTTPS。許可はボタンを押したときだけ求める |
| 大きな写真でメモリ不足になる | 取り込み時に長辺2160pxへ縮小 |
| iOSで撮ったHEIC写真 | ファイル選択時に端末側でJPEGに変換されるのが通例。読めなかった場合は「別の写真を選んでください」と出す |
| Instagramなどのアプリ内ブラウザでは、ファイル選択・共有・保存が制限されることがある | アプリ内ブラウザを検知したら「Safari／Chromeで開く」案内を1行出す。@hakko.3d のプロフィールから来る人の多くがここを通るので、公開前に実機確認が必須 |
| ファイル共有に対応しない端末がある | 7.3の2と3で縮退 |

### 7.7 プライバシー：何を持たないか

| データ種別 | 保持場所 | 保持期間 | 備考 |
|---|---|---|---|
| 元の写真 | ブラウザのメモリのみ | タブを閉じるまで | サーバーへ送らない。端末内保存もしない |
| 写真のEXIF（GPS・撮影日時・機種） | 持たない | — | 取り込み時の描き直しで消える |
| 生成したシェア画像 | ブラウザのメモリのみ | タブを閉じるまで | 保存先は利用者自身の写真アプリ等 |
| 記録の内容（プロセス・国・日付） | ブラウザのメモリのみ | タブを閉じるまで | 履歴として残さない |
| 最近の国・最近の店舗名・画像設定 | 端末内（localStorage） | 利用者が消すまで（ブラウザが消す場合あり） | 端末の外に出ない |
| 現在地の座標（正確な値） | ブラウザのメモリのみ | 検索1回の間 | 丸める前の値は端末から出ない |
| 現在地の座標（約100mに丸めた値） | プロキシと提供元を通過するのみ | プロキシでは保持しない。提供元側は提供元の規約による | 「近くの店を探す」を押したときだけ送信 |
| IPアドレス | ホスティング事業者・プロキシ基盤の通信処理 | 当方では記録しない。事業者側のログ保持は事業者の仕様による | 通信に不可避。レート制限のため一時的に参照するが保存しない |
| 氏名・メール・アカウント | 持たない | — | ログインなし |
| Cookie・広告ID・解析用の識別子 | 持たない | — | 解析ツールなし |
| サーバー側データベース | 存在しない | — | 流出するものがない |

**位置情報をサーバーへ送る範囲と理由**：送るのは丸めた座標のみ、送る場面は店舗検索の1回のみ、理由は近くの店舗候補を返すためです。プロキシを経由するので、提供元に届くのはプロキシのIPアドレスで、利用者のIPアドレスと座標が提供元で結び付きません。

**シェア画像に載る位置の粒度**：店舗名のみ。緯度経度・住所・地図は載りません。自宅は「HOME」のみです。

**利用者への表示**：トップのフッターに1行、プライバシー表記のページに上の表をそのまま載せます。店舗検索を有効にする段階で、外部へ送る情報の表示義務（電気通信事業法の外部送信規律）や個人情報保護委員会のガイドラインに照らした要否を、一次情報で確認します（未確認）。

### 7.8 セキュリティ

**APIキーの扱い：(a) 公開範囲の制限で足りるか、(b) プロキシが必須か**

| 観点 | (a) ブラウザに置き、リファラ等で制限 | (b) プロキシ経由 |
|---|---|---|
| キーの露出 | 誰でも見える | 見えない |
| 不正利用 | リファラは偽装できるため、枠の盗用を防ぎきれない | 自ドメインからの要求だけ受け、レート制限をかけられる |
| プライバシー | 利用者のIPと正確な座標が提供元へ直接届く | 座標を丸め、IPを提供元に渡さずに済む |
| 可用性 | 部品が少ない | プロキシが落ちると検索が止まる（手入力に縮退） |

**決定は (b)**。キーの保護だけなら (a)＋課金上限でも成り立つ場合がありますが、「座標を丸める」「利用者のIPを提供元に渡さない」はプロキシでしか実現できないためです。

**プロキシの設計（個人情報を持たない原則との両立）**
- 置き場所：静的ホスティングと同じドメインのエッジ関数。別ドメインにしない（通信先を増やさないため）。
- キーの保管：ホスティング基盤のシークレット設定（環境変数）にのみ置く。リポジトリ・設計書・クライアントのコードには書かない。設定例では `PLACES_API_KEY=<基盤のシークレット設定に登録>` のようにプレースホルダで示す。
- ログ：座標はURLではなく要求の本文で送り、アクセスログに残る経路から外す。プロキシ自身は要求内容を記録しない。エラー時も座標を出力しない。
- 入力の検証：緯度・経度が数値で範囲内であることだけを受け付け、それ以外は拒否する。提供元のURLは固定し、利用者の入力で宛先が変わらないようにする。
- レート制限：IPごと・全体の両方に上限を置く。IPは判定の間だけ参照し、保存しない。
- 課金上限とアラート：提供元側で1日の上限と予算アラートを設定し、上限に達したらプロキシが検索を停止して「手入力」へ縮退させる。
- 応答：店舗名と距離だけを返し、提供元の応答をそのまま流さない。

**通信とヘッダー**
- 全ページHTTPS。HTTPはHTTPSへ転送し、HSTSを有効にする。
- CSP：既定はすべて拒否。スクリプト・スタイル・フォント・通信は自ドメインのみ、画像は自ドメインと端末内生成（blob／data）のみ許可。インラインスクリプトは使わない。他サイトへの埋め込みは禁止（frame-ancestors 'none'）。
- そのほか：`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`Permissions-Policy` で位置情報を自ドメインのみに、カメラ・マイク等は無効に。
- 以上はHTTPヘッダーで設定します。ヘッダーを設定できないホスティング（例：GitHub Pages）は候補から外します。
- 店舗名・自由入力はCanvasへの文字描画と、文字列としての画面表示にのみ使い、HTMLとして解釈させません。

**依存ライブラリの選定基準**
- 実行時の依存はゼロを目標とする（画面・画像生成ともブラウザ標準機能で書ける規模）。
- 入れる場合の条件：直近1年以内に更新がある、既知の脆弱性が未修正で残っていない、ライセンスが明確、同じことが標準機能で50行以内に書けない。
- ビルド用の道具は最小限にし、バージョンを固定し、脆弱性の自動通知を有効にする。外部CDNからスクリプトを読み込まない。

**外部送信先の一覧（このサイトが通信する宛先のすべて）**

| 宛先 | いつ | 何を送る |
|---|---|---|
| 自ドメイン（静的ホスティング＋CDN） | ページを開いたとき | 通常のWeb要求（IP、ブラウザ情報）。利用者の入力は送らない |
| 自ドメインのプロキシ | 「近くの店を探す」を押したとき | 丸めた緯度・経度のみ |
| 店舗検索の提供元（プロキシから） | 同上 | 丸めた緯度・経度のみ。利用者のブラウザからは直接通信しない |

これ以外の宛先はありません（フォント配信、解析、広告、SNSの埋め込み、地図タイルのいずれもなし）。CSPがこの一覧を機械的に強制します。

### 7.9 可用性

**静的構成が効く理由**：配信するのは変化しないファイルだけなので、CDNの複数拠点から返せます。データベースもログイン処理もないため、障害の起きる部品自体がありません。アクセスが急増しても（@hakko.3d で紹介した直後など）サーバー側の処理が増えません。

**単一障害点と対処**

| 障害点 | 影響 | 対処 |
|---|---|---|
| 静的ホスティング／CDN | 初めての人が開けない | 一度開いた端末にはアプリ本体を端末内に保持し（Service Worker）、オフラインでも起動・画像生成できる |
| ドメイン・DNS | 同上 | ドメインの自動更新、登録事業者アカウントの二要素認証 |
| プロキシ | 店舗検索だけが止まる | 手入力へ縮退 |
| 店舗検索の提供元 | 同上 | 4秒で打ち切り、手入力へ縮退 |
| 欧文フォントの読み込み | 見た目が変わる | 端末の標準フォントで描画。生成は止めない |
| 運用者（1名） | 更新できない | ソースと公開手順をリポジトリに置く。秘密情報は基盤側のみ |

**縮退の段階**

| 状況 | 使える機能 |
|---|---|
| すべて正常 | 全機能 |
| 店舗検索が停止（障害・上限到達・位置情報の拒否） | 店舗名の手入力＋最近の店。記録と画像生成は完結 |
| 完全にオフライン（2回目以降の端末） | 写真選択、入力、画像生成、保存 |
| ホスティング停止かつ初訪問 | 利用不可（唯一の残存リスク。静的配信の稼働率に依存） |

「核機能（画像生成）は外部サービスが全滅しても動く」は、一度でも開いた端末については満たします。初訪問の端末だけは配信元が必要で、これは原理的に外せません。

**満たせない前提・緩めた前提**：ありません。上の「初訪問時は配信元が必要」と「IPアドレスが事業者の通信処理を通る」は、Webサイトである以上避けられない事項として、7.7と本節に明記しました。
